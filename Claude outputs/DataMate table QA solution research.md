# Clean the data first, then distill the agent

The strongest DataMate entry will come from engineering around the model, not from finding a better one. No public repository solves this task end to end. Start from the Gradiant MRT_TableQA skeleton, the only SemEval-2025 DataBench system with public code that runs entirely on open models of 14B or fewer. Rebuild it as a fixed, non-ReAct pipeline with six parts: a deterministic per-business loader that writes DuckDB tables, the rulebook compiled into tested helper functions, structured intent extraction, diverse pandas and SQL candidates voted on canonicalised answers, a calibrated abstention gate, and a pure-code answer formatter. For the model, host **Qwen3.5-9B** (Apache-2.0, released Feb–Mar 2026, with the strongest published small-model tool-use scores) as two BF16 vLLM replicas, one per RTX 5090. Keep **Qwen3-14B in FP8** as the fallback in case Qwen3.5's hybrid DeltaNet layers fail rerun-determinism tests, because Qwen3 is on vLLM's validated batch-invariance list and Qwen3.5 is not. Training should be LoRA SFT on teacher trajectories that pass rejection sampling, drawn from the 3,000 training questions plus synthetic businesses written under *randomised Vietnamese rulebooks*. Published recipes of this kind lifted a 14B coder from 56.6% to 71.2% on data-agent benchmarks. RL with verifiable rewards is a stretch goal for a three-week window. Under +1/0/−1 scoring, answering only pays when P(correct) exceeds 0.5. Self-reflection and raw vote agreement are poorly calibrated, so set the abstention threshold with a logistic model fitted on business types held out from training. The open risks are mostly about rules and need answers from the organisers this week: whether vision-encoder and MTP parameters count toward the 15B, whether teacher or API models may generate training data, and exactly how answers are canonicalised.

## No repo solves DataMate, so fork MRT's skeleton and build a fixed pipeline

The closest benchmark is SemEval-2025 Task 8 (DataBench), which also asks typed, exact-match questions over real tables. LLM code generators dominated it, and larger models did considerably better than smaller ones ([SemEval-2025 Task 8 overview](https://preview.aclanthology.org/setup/2025.semeval-1.324)). The winner, TeleAI, scored **95.02** with a program-based "Flow-of-Table-Reasoning" framework: schema linking that keeps only the columns relevant to the query, plus an iterative reflection loop. It published no code and did not name its model ([benchmarklist DataBench](https://benchmarklist.com/benchmarks/databench/); [TeleAI](https://aclanthology.org/2025.semeval-1.240)). Gradiant's MRT is the useful skeleton. Its pipeline runs a cached per-table column descriptor, an explainer, a pandas coder with a runner that retries up to three times, a type interpreter and a rule-based formatter. It uses only open models up to 14B, and a single **Qwen2.5-14B scored 0.665 on test against 0.667 for the full ensemble** ([MRT paper](https://arxiv.org/pdf/2505.22264)). MRT also carries a warning for DataMate: formatting heuristics introduced new errors (dev accuracy fell from 0.772 to 0.766 at the formatting step), and **formatting caused roughly 10% of the remaining errors** ([MRT paper](https://arxiv.org/pdf/2505.22264)). The gap between MRT (~0.67) and TeleAI (~0.95) shows how much a well-designed harness adds on top of the model.

The other candidates are design references rather than forks. Google's DS-STAR combines a per-file analyzer script, planner, coder, LLM verifier, router and debugger. It hit 87.5% easy and 45.2% hard on DABstep with Gemini-2.5-Pro, which fell to **79.2% and 28.6% with open-weight DeepSeek-V3**, and it released no code ([DS-STAR](https://arxiv.org/pdf/2509.21825)). MATA runs CoT, Python and SQL paths over 3–8B models with small auxiliary tools: a MobileBERT scheduler, a DeBERTa confidence checker and a 0.5B format matcher. Its confidence-gated design is the closest published analogue to DataMate's abstain decision ([MATA](https://arxiv.org/pdf/2602.09642)). DeepAnalyze-8B is an MIT-licensed agentic data-science model that serves directly on vLLM ([HF card](https://huggingface.co/RUC-DataLab/DeepAnalyze-8B/blob/refs%2Fpr%2F1/README.md)). Nobody has published how it does on exact-answer QA, so it belongs in the model bake-off and should not be the default. Heavier frameworks (OpenHands, MetaGPT, PandasAI, TableGPT-agent) are either too slow for a ~43-second-per-question budget or too weak. TableGPT2-7B scored **0.066 on DataGovBench** ([DataGovBench](https://arxiv.org/pdf/2607.06482)). GitHub could not be reached during this research, so check licences and activity for every repo by hand before forking.

Choosing between pandas and SQL decides how the loader should be built. On clean schemas (BIRD), small models make fewer errors in SQL: Qwen2.5-Coder-7B scores **35.95% in Python vs 52.93% in SQL**, and logic errors occur in 17.5% of Python outputs against 0.3% of SQL outputs. Adding domain clarifications lifted Qwen3-7B to about 71% in both languages ([Text-to-Python vs Text-to-SQL](https://arxiv.org/html/2601.15728v2)). On messy real-world multi-table data the result flips. Python beat SQL **0.545 vs 0.241** with Gemini-2.5-Flash on DataGovBench, where condition-filter errors (32.4%) and transformation errors such as day-first dates and "1,234,567" strings (23.2%) dominated ([DataGovBench](https://arxiv.org/pdf/2607.06482)). Together these results suggest a split. Python should do the messy wrangling, once and deterministically, in a hand-written loader. The model then queries clean DuckDB tables in SQL or pandas, with both paths voting. The 30 training businesses expose the full range of mess (forward-fill blanks, duplicate export rows, one sheet per month, split files, "1.250.000đ" amounts), so the team can write loaders for each file pattern and unit-test them against the 3,000 reference answers.

| Layer | Recommended component | Basis |
|---|---|---|
| Ingestion | Deterministic per-business loader → DuckDB/parquet with `source_sheet`/`source_period` columns, a dedup log, VND parsing and unit conversion. Forward-fill dimension columns only | DataGovBench error classes; DS-STAR and MRT profiling |
| Context | Auto-generated schema card (dtypes, date min/max, sample distinct values) plus top-k value retrieval | MRT column descriptor; Anotheroption value retrieval |
| Semantics | Rulebook compiled into parameterised helpers (`resolve_period`, `net_revenue`, `rank_with_ties`, `tet_window`) plus a config file | TroVE / ReGAL library learning; BIRD clarification gains |
| Understanding | NFC normalisation, a teencode dictionary, diacritic-insensitive entity matching, and a JSON intent with an `answerable` flag | VietNormalizer limits; CHASE-SQL decomposition |
| Generation | N candidates across pandas and SQL, with 1–2 repair turns on exceptions | Anotheroption, AIMO-2 |
| Selection | Clustering on canonicalised answers, early stopping, and a calibrated abstain gate | AIMO-2; 2026 selective-prediction study |
| Output | Pure-code typed formatter matched to the grader | MRT formatting-error lesson |
| Serving | vLLM, two data-parallel replicas, batch-invariant mode, warm subprocess sandbox pool | vLLM docs; CloudRift RTX 5090 data |

## Qwen3.5-9B leads the eligible field, with Qwen3-14B as the determinism fallback

The 15B *total* parameter rule rules out most popular "small" agents: gpt-oss-20b (~21B total), Gemma 4 26B-A4B and 31B, every Qwen3.6 model, and the larger Qwen3.5 sizes ([models listing](https://artificialanalysis.ai/articles/qwen3-5-small-models); [Qwen3.6 launch](https://docs.apiyi.com/en/news/qwen-3-6-opensource-launch); [LM Studio gpt-oss-20b](https://lmstudio.ai/models/openai/gpt-oss-20b)). Among eligible models, **Qwen3.5-9B** has the best published agentic profile. It scores BFCL-V4 66.1, τ2-Bench 79.1, LiveCodeBench v6 65.6, IFEval 91.5 and MMMLU 81.2 (gpt-oss-20b: 69.7), with 262K native context, 201 languages and an Apache-2.0 licence ([Qwen3.5-9B card](https://deepinfra.com/Qwen/Qwen3.5-9B)). **Gemma 4 12B** (3 Jun 2026, ~11.95B dense, Apache-2.0) reports a higher LiveCodeBench v6 of 72.0 but publishes no tool-use scores, and those figures come from a secondary source ([Google Gemma releases](https://ai.google.dev/gemma/docs/releases?hl=en); [aicybr guide](https://aicybr.com/blog/gemma-4-12b-accurate-guide)). Qwen3.5-9B has three weaknesses worth testing. It produces very long reasoning traces (about 260M output tokens to run Artificial Analysis's index, against about 98M for the 27B). It hallucinated at an 82% rate on AA-Omniscience ([Artificial Analysis](https://artificialanalysis.ai/articles/qwen3-5-small-models)). And its hybrid Gated-DeltaNet architecture is not on vLLM's validated batch-invariance list, which includes Qwen3, Qwen2.5, Mistral, GLM-4 and Phi but not Qwen3.5 or Gemma 4 ([vLLM batch invariance](https://docs.vllm.ai/en/latest/features/batch_invariance/)). No public DABstep, TableBench or BIRD numbers exist for either 2026 model, so the decision has to come from a local bake-off.

| Candidate | Total params / licence | Why consider | Main risk |
|---|---|---|---|
| **Qwen3.5-9B** (primary) | ~9B (vision encoder inclusion unclear) / Apache-2.0 | Best BFCL/τ2, multilingual, leaves ~6B headroom | Not batch-invariance validated; verbose thinking |
| Gemma 4 12B | ~11.95B / Apache-2.0 | Strongest small-model code score | No agentic scores; ~3B headroom; not validated |
| Qwen3-14B (fallback) | ~14.8B / Apache-2.0 [prior knowledge] | On vLLM's validated determinism list; mature tooling | Older; needs FP8 to fit one 32 GB card |
| DeepAnalyze-8B | ~8B / MIT | Purpose-built data agent | Unproven on exact-answer QA |
| Arctic-Text2SQL-R1-7B/14B | 7.6B / 14.7B, licence unconfirmed | BIRD-dev 68.9 / 70.1 | SQL-only, English-centric ([Arctic](https://arxiv.org/html/2505.20315v2)) |

Run Qwen3.5-9B in **BF16** (about 18 GB of weights, which leaves room for KV cache on a 32 GB RTX 5090). Use **two independent vLLM replicas**, one per GPU, rather than tensor parallelism. At this size the model fits on one card, the 5090s have no NVLink, and TP all-reduce is an extra source of nondeterminism. Any 12–14B fallback should run in FP8, which vLLM handles natively on Blackwell. On RTX PRO 6000, by contrast, SGLang needed several triton and cache workarounds to run FP8 ([CloudRift](https://www.cloudrift.ai/blog/optimizing-qwen3-coder-rtx5090-pro6000)). Avoid 4-bit weights. In AIMO-2, a 14B model lost about **9 points on AIME24 under W4A16**, while FP8 plus speculative decoding gave 554 vs 210 tok/s with little accuracy loss ([AIMO-2](https://arxiv.org/pdf/2504.16891)). The model card launch command is `vllm serve Qwen/Qwen3.5-9B --reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder`, and at launch it needed a vLLM nightly ([Qwen3.5-9B card](https://deepinfra.com/Qwen/Qwen3.5-9B)). Pin a stable `vllm/vllm-openai` tag built for CUDA 12.8+ (needed for sm_120), bake the weights into the image, and set `HF_HUB_OFFLINE=1`. Throughput is not the binding constraint. Six hours for 500 questions is about **43 s per question serially**, and one RTX 5090 sustained about **1,157 tok/s aggregate at 16 concurrent requests** on a 30B-A3B AWQ model ([CloudRift](https://www.cloudrift.ai/blog/optimizing-qwen3-coder-rtx5090-pro6000)). Running questions concurrently across two replicas leaves room for 8–16 samples per question.

Determinism is the binding constraint. vLLM's batch-invariant mode (`VLLM_BATCH_INVARIANT=1`, greedy or fixed seed) promises identical outputs regardless of batch composition. It is beta, requires compute capability 8.0 or higher, and lists RTX 5090 as qualifying but not validated ([vLLM batch invariance](https://docs.vllm.ai/en/latest/features/batch_invariance/)). The test for week 1 is simple: run the full held-out set three times on Qwen3.5-9B with batch invariance on, and count answer flips. Here is a rough sense of scale, assuming the score is normalised per question: one correct answer flipping to wrong moves the score by 2/500 = 0.004, so roughly seven such flips use up the 0.03 tolerance. If Qwen3.5 flips more than two or three answers per run, switch to Qwen3-14B FP8, or serialise requests within each replica. Use the leftover parameter budget only once an ablation shows it pays. A Qwen3.5-4B second sampler or verifier would bring the total to about 13B; it scores close to the 9B on τ2 (79.9) but well below it on code (LCB 55.8) ([Qwen3.5-9B card](https://deepinfra.com/Qwen/Qwen3.5-9B)).

## Teacher-trajectory SFT under randomised rulebooks is the main training lever

The closest published precedent is **DataMind**. It sampled three DeepSeek-V3.1 trajectories per synthesised query over CSV, XLSX and SQLite, kept only those whose answers agreed, and fine-tuned on 11,707 of them followed by DAPO RL. That raised **Qwen2.5-Coder-14B from 56.64% to 71.16%** averaged over DABench, TableBench and BIRD, slightly above DeepSeek-V3.1 (70.58%) and GPT-5 (69.44%). The 7B rose from 11.26% to 68.10% ([DataMind](https://arxiv.org/html/2509.25084v3)). Table-r1 likewise found that distillation cold-start gives the largest gain in its ablations ([Table-r1](https://arxiv.org/html/2506.06137v1)). The plan follows from this. Run a strong teacher inside the exact final harness, with the same helper API, schema-card format, prompt layout and answer types. Sample 4–8 trajectories per question. Keep only trajectories whose formatted answer matches the reference under the competition's own scorer, and mask observation tokens and turns with no valid code or answer, as DataMind does. Then train LoRA on all linear layers, including the MLP. Thinking Machines showed this matches full fine-tuning for SFT at this data scale, with a learning rate about 10x the full-fine-tuning rate ([LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)). Whether a teacher may be used at all is a rules question (see the final section). If it cannot, generate trajectories with the base model itself under high-N rejection sampling.

The hidden test introduces new business types and a *different rulebook*, so the biggest training risk is memorising the training rulebook. Reason-SFT lost **14.69 points under row and column perturbation versus 5.95 for RL-zero** ([Reasoning-Table](https://arxiv.org/html/2506.01710v1)), and SQL models fine-tuned only on Spider and BIRD generalise poorly to new domains ([OmniSQL](https://arxiv.org/html/2503.02240v2)). OmniSQL's remedy, synthesising diverse databases, then questions in many styles, then answers verified by execution, works with open models ([OmniSQL](https://arxiv.org/html/2503.02240v2)). It needs one adaptation for DataMate. Write a Python generator for new Vietnamese SME types such as a spa, garage, pharmacy, café chain or tutoring centre. Have it inject realistic mess and compute every answer with trusted code. Then **randomise the rulebook**: Sunday-start weeks, revenue that includes returns, alternative tie-breaks, different debt-aging buckets. Write each variant in Vietnamese and recompute the answers under it. A model trained this way learns to read the rulebook in context and turn it into code. No published study has measured this exact technique, so treat it as a strong hypothesis and validate it by holding out entire business types along with a perturbed rulebook. Filter synthetic items so that at least one of N teacher attempts reaches the programmatic answer. Arctic found that unfiltered synthetic data *lowered* scores, while data filtered on "≥1 of 10 correct" helped ([Arctic-Text2SQL-R1](https://arxiv.org/html/2505.20315v2)). Add paraphrases in Vietnamese without diacritics, in teencode and with code-mixing, and oversample unanswerable questions so the model learns to emit that answer type.

RL adds smaller and slower gains. GRPO with a binary execution-match reward lifted Qwen2.5-Coder-14B on BIRD-dev from **61.5 to 70.1**, but that run started from a strong SFT checkpoint. Shaped rewards caused "lazy" reward hacking, and 16, 24 or 32 rollouts performed the same ([Arctic-Text2SQL-R1](https://arxiv.org/html/2505.20315v2)). Multi-turn RL (inspect, then compute) reportedly reaches its reward target 2.8x faster than single-turn RL on the same data ([SkyRL-SQL summary](https://machinelearningatscale.substack.com/p/text-to-sql-just-got-a-lot-better)). Abstention via RL is fragile. With r_abs = 0.3, one model collapsed to **100% "I don't know"**, and RL alone cannot teach abstention to a base model that never abstains ([Rewarding Intellectual Humility](https://arxiv.org/html/2601.20126v1)). The training notes estimate, as reasoning rather than measurement, that multi-turn GRPO on a 14B model takes roughly 4–8 H100s for days. A three-week schedule that must also build the harness therefore cannot count on RL. Treat a short GRPO run on the SFT model as optional for week 3. Use the scorer as a binary reward, restrict training to questions with a pass rate strictly between 0 and N, and use verl or SkyRL with a subprocess sandbox identical to the inference one. Keep abstention out of training altogether and handle it at inference.

## Calibrated abstention beats self-reflection under +1/0/−1 scoring

A wrong answer costs as much as a right answer earns, so answering only adds expected value when **P(correct) > 0.5**. The 2026 selective-prediction study on BIRD gives the most direct evidence on how to estimate that probability. Executability predicts correctness at chance (**AUROC 0.500**). Execution self-consistency reaches only **0.613**, and string self-consistency 0.675. Verbalised self-confidence after self-correction was 0.637, with an ECE of 0.501 and a mean confidence of 0.97. Self-consistency alone found no low-risk subset to answer at any tested target. A calibrated ensemble of two judges reached 0.822 AUROC, but verifiers trained on in-distribution data fell to about **0.66 on unseen databases** ([selective-prediction study](https://arxiv.org/pdf/2607.06799)). For DataMate, the confidence model should combine several weak signals rather than trust any single one. Fit a logistic model on held-out business types using these features: top-cluster vote share, the margin to the runner-up, crash fraction, agreement between pandas and SQL candidates, and the deterministic rule-check flags. Then pick the threshold that maximises summed +1/0/−1 score, not accuracy. Diverse generators matter here. In the Anotheroption SemEval system, adding SQL candidates to Python ones raised dev accuracy to 84%, and the full multi-model ensemble reached **88% dev vs 74% for GPT-4o alone**. In the same system, self-correction "contributed little", and free-text question reformulation *hurt*, lowering one path to 68% and another to 52% ([Anotheroption](https://arxiv.org/html/2506.09657v2)).

The selection step has room to improve. AIMO-2's winning 14B system measured **maj@16 = 69.1 against pass@16 = 81.3**, about 12 points that voting leaves on the table. GenSelect pairwise comparison recovered 1.5–2 points of that ([AIMO-2](https://arxiv.org/pdf/2504.16891)). The same system shows how to fit voting into a time budget. It limited each sample to six code calls with 2-second timeouts and 200 characters of fed-back output, stopped early once 4–5 samples agreed, and banked time from easy questions for hard ones ([AIMO-2](https://arxiv.org/pdf/2504.16891)). Few-shot retrieval adds a little more. With DAIL-SQL, masking entities before matching on similarity raised GPT-4 5-shot Spider-dev accuracy from 79.5 (random examples) to 82.0, and adding skeleton similarity raised it to 82.4 ([DAIL-SQL](https://raw.githubusercontent.com/BeachWang/DAIL-SQL/main/README.md)). Gains of that size could plausibly be larger for a 9B model working under an unfamiliar rulebook.

The table below ranks improvements by expected net-score impact per unit of effort. The impact column is the team's reasoned estimate, not a measurement on DataMate. Validate every row on held-out businesses before keeping it.

| Priority | Idea | Expected impact | Evidence anchor |
|---|---|---|---|
| 1 | Deterministic per-business loader + schema card | Very high: removes the dominant error class on messy files | DataGovBench: 23% transformation, 32% filter errors |
| 2 | Rulebook compiled into tested helpers + config | High: turns rule semantics into function calls; shrinks programs and raises vote agreement | BIRD clarification +10–18 pts; TroVE |
| 3 | Calibrated abstain gate (P>0.5) | High under −1 scoring: converts likely-wrong answers into zeros | Selective-prediction AUROC data |
| 4 | Pure-code typed formatter matched to grader | Medium-high: ~10% of residual errors in MRT | MRT |
| 5 | Teacher-trajectory LoRA SFT with randomised rulebooks | High (DataMind +14.5 pts at 14B), with risk of overfitting to the domain | DataMind, Reasoning-Table |
| 6 | Pandas + SQL candidates, canonicalised clustering, early stop | Medium: more accuracy and a better confidence signal | Anotheroption, AIMO-2 |

| 8 | JSON intent with `answerable` flag + deterministic out-of-range checks | Medium: catches unanswerable questions and period errors cheaply | CHASE-SQL decomposition |
| 9 | Masked-intent few-shot retrieval of solved examples | Low-medium | DAIL-SQL +2–3 pts |

The Vietnamese layer needs care rather than another model. Neural diacritic restoration reaches about 96–97% accuracy on clean text ([MT diacritic restoration](https://arxiv.org/abs/1709.07104)). VietNormalizer covers numbers, dates, currency and acronyms, but it explicitly does not handle teencode or restore diacritics ([VietNormalizer](https://arxiv.org/pdf/2603.04145)). That means a dictionary mined from the 3,000 training questions ("dthu", "bn", "sp", "kh"), plus accent-stripped fuzzy matching against canonical entity names, does most of the work. String answers should always be copied from the data's canonical value, so their diacritics are correct by construction.

Several technical risks remain unresolved. Nobody has confirmed that vLLM's batch-invariant kernels cover Qwen3.5's DeltaNet layers or Gemma 4 on sm_120. No RTX 5090 throughput figures exist for any 9–14B candidate. No published study measures rulebook randomisation, Vietnamese table QA, or abstention for code-executing table agents. The training-compute estimates come from reasoning rather than sources, and the team has not stated what GPUs it has beyond the two 5090s used for inference. Finally, the MRT, smolagents and DeepAnalyze repositories could not be checked on GitHub for licence or recent activity.

## Conclusion

DataMate looks like a model competition but mostly tests the system around the model. The +1/0/−1 metric rewards knowing when the system is wrong, and the hidden rulebook rewards reading rules in context rather than memorising them. Both point to the same strategy: move semantics out of the model and into tested code (loaders, helpers, formatter), then use the model's stochasticity as a confidence signal rather than relying on its self-assessment. The parameter cap changes this less than it seems. A 9B model calling a well-built helper library over clean tables has a much easier job than a 14B model parsing raw spreadsheets, and the parameters it leaves unused are a reserve for a verifier, not a handicap.

The highest-leverage decision this week is not which model to pick. It is building the held-out evaluation correctly: whole business types held out, combined with a perturbed rulebook, scored with the organisers' exact canonicalisation. Every later choice depends on that number: model, SFT mix, abstention threshold, and whether RL is worth attempting. A team that builds this evaluation first will make better decisions for the rest of the competition than a team with more GPUs that judges itself on a random split of the training rulebook.
